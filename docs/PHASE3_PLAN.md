# 第三阶段：八个投研台补齐与数据湖日更

本阶段在 YunAlpha 继续八台建设，同时在独立的数据湖项目整理近期发布和更新机制。Agent 联动、配置报告、指增报告、策略扩展和 Autoloop 实装暂缓。

## 八个投研台：先定位缺口，再决定补不补

YunAlpha 从 `7652ed4` 开始执行；分批状态见[总控执行登记](tasks/phase3-control.md)。保留第二阶段冻结快照作对照；以[已登记缺口](../apps/vic_desks/evidence/seven/DATA-GAPS.csv)和湖侧近期发布记录重新逐项核对，避免把快照里的缺项误判成湖里没有。

1. **查口径**：用 REA 核对 VICAlpha 用户界面可见的定义、日期、筛选、单位和结果样本。优先处理会影响排序、历史回看和横向比较的指标。同一日期和样本做对照，记录「已验证口径」「明确的本地口径／近似」「未知或暂缓」。
2. **补取数**：先用正式湖及已有原始响应；确实缺且价值高时，用 DS 做少量标的、日期的取数验证，确认覆盖、字段、额度和耗时，再决定是否补。大规模历史回填、逐份抓公告、长时间全市场抓取以及来源不稳定的数据，本期跳过或缩短覆盖期，页面标明缺失或近似。
3. **落实现有模块**：业务指标与看板交互留在 YunAlpha；须长期复用的通用数据由湖侧发布。先对照公募抱团和市场估值两种样板，其余六台按缺口优先级推进。每台有明确已补项、可对账样本和剩余缺口；保留筛选、图表和下钻。

## 独立数据湖：先保全与核对，再调整日更

项目为 `/path/to/local-user/项目/多资产智能投研平台-v2`。规划核对时，本地当前提交为 `7dd2f16`，已有大量修改和新增补采脚本。既有 LaunchAgent `com.multiassetlake.daily` 已装载，实际触发配置为 16:05；核对时处于运行。启动开发前核实实际状态，从已有成果做保护性基线，不从旧提交另开空白工作树覆盖，也不与运行中的任务抢写。

1. **盘点新数据和现状**：对照注册表、正式数据、发布收据、更新水位和下游实际读取，区分正式发布、待验证候选、一次性快照和计算产物。对近期新增数据重点查主键重复、分区覆盖、日期和单位、可读性及与既有表的冲突。源码和文档按范围保全，运行数据留在湖侧。
2. **补齐逐表上游清单**：对所有数据集登记来源、接口或生成命令、已有覆盖、发布时间、更新频率及当前状态。区分日更、定期披露、依赖其他表计算、一次性快照，以及无可靠自动来源。先实测日更所依赖的接口和本机运行环境；权限不足、上游停供或临时补数不能当成日更能力。
3. **将既有调度改为 18:00（Asia/Shanghai）启动**：复用 `scripts/daily_pipeline.sh` 和原 LaunchAgent。日频数据按各自交易日更新；基金净值等晚到数据按现有补抓机制验证，季报与低频数据按其实际披露周期处理。先用分组增量跑通，原任务结束后切换，只留一套写入调度；验收至少观察一次真实的 18:00 触发，并核对运行结果及重点数据的截止日期。
4. **给中台留接管点**：沿用一个可单独触发的更新入口和一份可读取的运行摘要，包含数据日期、成功／迟到／失败的分组。后续 Autoloop 只接管触发与状态收集，湖仍负责取数、计算和发布。本阶段不安装新中台。

## 总控与并行

总控加三条开发线，最多同时三条。湖侧单独开一个长期对话；其余两条复用已有对话，一组完成后可回到同一对话领取下一批任务。开发对话保持 `gpt-6.1-sol / high`。

| 线 | 责任和修改范围 |
|---|---|
| B · 公募及机构类 | 在 YunAlpha 补公募抱团、公募持仓、国家队全景、逆向投资。优先样板：公募抱团。 |
| 看板第二线 · 市场类 | 在 YunAlpha 补市场估值、情绪温度计、全 A 筹码结构、A 股资金流。优先样板：市场估值。 |
| 新对话 · 数据湖 | 在独立湖仓推进保全、审计、源清单、增量更新与原调度交接；统一管理需写正式湖的新数据。 |

看板线先做样本与缺口归因，不等全湖整理完；需补数据时说明「指标、范围、源字段、频率和样本」，由湖侧统一决定取数及发布。通用看板代码和共享启动配置由总控协调，避免两条线同时修改。每条任务从确认后的提交起建独立工作树；调度切换和正式湖写入只在湖侧统一进行。

交付以八台逐项对账、已知缺口清单、逐表上游清单和实跑记录为准。不重复全量历史回填，不把近似指标描述成 VICAlpha 原算法，不部署 YunAlpha。
