# 数据湖与投研台日更

YunAlpha 负责发起和记录本机日更，数据湖仍维护采集、发布和报告程序。macOS 按北京时间 18:00、21:30 和用户登录触发同一个 `com.multiassetlake.daily` 任务。18:00 后查本次，18:00 前查上一个调度日。目标交易日用数据湖的交易日历计算。开机但未登录时，用户后台任务尚未启动。

## 使用与接管

- `./scripts/daily_update.py --check` 只读检查湖与投研台、显示当前可执行动作，不发起外部取数或 DSH 请求。
- `./scripts/daily_update.py` 手动续跑最近一个调度日。它与后台任务共用锁和回执。指定 `--slot-date YYYY-MM-DD` 可检查或补一个具体调度日。历史快照按湖的既有规则跳过并列明，已经切换到较新日期的看板不回退。
- `.runtime/daily-update/latest.json` 是最近一轮的机器可读摘要，另按交易日保留检查点，每次运行的独立摘要和日志按实际启动时间保留。分别看 `lake.status`、`desks.status`、`maintenance`，及分组的 `pending`、`manifest` 和 `repair_receipts`。API 如已运行，同时读回实际服务版本；API 关闭时检查下次启动将加载的版本。状态 `waiting` 表示尚有缺口，本轮没有到时可执行的动作。中台以后调用同一入口并读回 JSON。
- `./scripts/install_daily_update.py --preview` 查看拟更新的 macOS 配置。主工作区执行同一命令去掉 `--preview` 重新安装。沿用原任务名称和日志，切换时保留原 plist 于 `.runtime/daily-update/com.multiassetlake.daily.before-yunalpha.plist`。需要恢复时，先确认任务空闲，再卸载当前项、恢复原 plist 并重新加载。

## 完成条件与续跑

湖侧用已有任务回执和正式分区分别确认分组是否执行、对应目标日期是否有数据。定向补抓可以完成原任务中未成功的步骤。已有正式日期只证明数据到达。源端历史快照不能回填时，摘要列出跳过的步骤。21:30 是晚到数据检查点，未到齐的继续留在摘要。正常补跑使用湖已有的增量窗口和定向命令，不为日更自动触发深历史回填。

投研台使用现有八台刷新入口和候选版本验证。核心湖数据就绪后才刷新。按发布文件和构建代码的版本判定是否需要重建，受影响的两套构建器各自复用可用结果。日期、版本以及保留的低频指标状态见看板自己的回执。新闻情绪计算、湖侧报告及例行维护排在看板之后，结果分别记录。

OpenCodex 代理就绪后启动独立的 DSH headless 配置。固定使用 `opencode-go/deepseek-v4.1-flash`，以代理的实际请求回执核对。DS 读取本轮状态，选择登记的分组、定向补抓或投研台刷新等动作，写入结论。由程序执行命令并验证结果，模型可以记录及调整本轮动作。接口变动、需要源码修复的问题由总控处理。认证如需变化，用本机环境中的 `YUNALPHA_DSH_PROXY_KEY`，部署凭据由本机配置保管。

## 随改随更新

修改湖分组或回执、投研台的正式输入或刷新接口、DSH 或 OpenCodex 的启动和路由时，同时核对 `config/daily-update.json` 与这份说明。投研台新增输入时，先确认是否已在公募抱团共用输入列表中，再登记七台新增输入。变更后运行 `--check`，涉及模型或调度的变更再做一次对应后台验证。

切换前的真实验收命令是 `./scripts/daily_update.py --verify-resume --slot-date YYYY-MM-DD`。它使用独立回执，并要求该日期已入湖且仍为投研台当前日期。第一次只走看板刷新，第二次核对幂等。正常调度不使用这个验收开关。
